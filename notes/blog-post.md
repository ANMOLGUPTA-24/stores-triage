# The hardest thing to build was an agent that does nothing

*Field report from the WeMakeDevs Agent Harness Hackathon — one week, one narrow
job, and four bugs that were each more interesting than the feature they broke.*

---

A part drops below its reorder level at a locomotive works and an alert fires.
The stores officer now has to answer a question the alert cannot: **is this
real?**

The evidence lives in three systems that do not talk to each other — the
consumption log, the open indents, and the consignments in transit. He gets
twenty of these a day and about forty minutes each. So in practice he either
raises the indent to be safe, or lets it sit.

Both mistakes cost. Raise a duplicate indent against stock already in transit
and the works pays expedite rates on stock it already owns. Miss a real shortage
and a locomotive sits idle.

I built an agent for that one job. The interesting part is not that it raises
indents. It is that **the demo is built on two alerts that are indistinguishable
from the alert alone** — 9.3 days of stock against 9.4 — where one is real and
one is not, and the correct answer to the second is to do absolutely nothing.

Most agent demos cannot do nothing. They are built to act, so an agent that
declines looks broken. Being confidently right that nothing should happen is the
harder half of the problem, and it is the half that saves the money.

## Two design decisions that did the heavy lifting

**Subagents are hypotheses, not subtasks.** Four competing explanations for why
the shortage might be on paper only — `consumption_spike`, `inbound_delay`,
`duplicate_indent`, `bom_change` — one subagent each, running in parallel. Every
one is trying to prove the shortage is *not* real. Ruling all four out is what
makes it real. That is differential diagnosis, not a work queue, and it is why
the reasoning is legible on screen: four columns, four verdicts, four pieces of
evidence.

**The agent never asks for permission bare.** An approval is only worth
something if the human can check it in five seconds, so every gate carries a
dossier: the queries run, the numbers, the chart, the exact payload about to be
sent, and one line stating what would change the recommendation. That last line
is generated by the rule that *almost* fired, not by the model, which is why it
is always specific:

> *If consignment CN-8821 is confirmed and lands by 2026-08-29, do not raise
> this indent.*

And the verdict itself is not the model's opinion. Adjudication is ordinary
Python with unit tests — four ordered rules, each stating why it fired. The
agent gathers evidence and calls tools; it does not get a vote. That is what
lets the do-nothing case pass in CI **with no model involved at all**.

## Then the week actually happened

### 1. A bare agent sends 67,358 tokens before you add anything

I measured this by reading Groq's 413 responses as a ruler. A TrueForge agent
with no MCP servers and no skills sends **67,358 tokens** per request. My MCP
server and skill added about 2,300 more; every feature toggle turned off
together saved about 1,500.

Groq's free tier is 8,000 tokens per minute. So no TrueForge agent can make a
single call on it — not a tuning problem, an arithmetic one. That one number
killed a provider before I wrote a line against it.

### 2. The local sandbox never had network, and I misdiagnosed it for three days

This is the one worth your time if you run TrueForge on Linux.

The symptom: the sandbox comes up, and the first thing it does — `pip install
pydantic` into its own venv — fails. The story I believed was *"the sandbox is
offline, so stage wheels and set `PIP_NO_INDEX`."* I staged a wheelhouse. I
verified it by reproducing the exact step inside `bwrap` by hand. It worked.

It never worked through the harness. Both halves of that story were wrong.

**The wheelhouse was never consulted.** The harness builds the sandbox's
environment from scratch — `childEnv = {...commandEnv(...)}` — so `PIP_NO_INDEX`
and `PIP_FIND_LINKS` set on the harness process never reach it. What I had
verified was bubblewrap, not the harness. That is why it survived three days.

**And the sandbox is *supposed* to have network.** `pypi.org` and
`files.pythonhosted.org` are both on TrueForge's own allowed-domain list.

The real fault is a mismatch between two layers. The sandbox reaches its
filtering proxy over a Unix socket that the sandbox runtime creates at
`os.tmpdir()/claude-http-<id>.sock`. But TrueForge's Linux allow-read list is:

```
/usr/bin /bin /usr/sbin /sbin /lib /lib64 /usr/lib /usr/lib64
/usr/local /etc /dev /proc /sys   + the sandbox-runtime vendor dir
```

No `/tmp`. The sandboxed process cannot see the socket, so every outbound
connection dies with `curl: (56) Proxy CONNECT aborted` — and `pip install`, the
very first thing a new sandbox does, always fails. On Linux that makes the local
sandbox unusable, and it takes skills with it, because skills require a sandbox.

I proved it instead of guessing, by driving the sandbox runtime's own CLI with
TrueForge's exact filesystem policy. One variable, no model involved:

| policy | result |
|---|---|
| `allowRead: ["/"]` | `pypi HTTP 200` |
| TrueForge's real policy | `curl: (56) Proxy CONNECT aborted` |
| TrueForge's real policy **+ `/tmp`** | `pypi HTTP 200` |

The fix needed no patching of the package. TrueForge adds one more path to the
allow-read list at runtime — the Code Mode socket parent, which it computes as
`os.tmpdir()/tf_cms` and then `realpath()`s. So point `TMPDIR` at a short
directory you own, and make `tf_cms` inside it a symlink back to its own parent.
The allowed path becomes `TMPDIR` itself, which is where the proxy socket lives.

The link has to be made *after* the server boots, because the harness `rm -rf`s
that path on startup and only reads it when the first sandbox is created.

Cost of finding it the expensive way, before I wrote a watchdog: **fifteen model
requests out of a daily allowance of twenty**, spent watching an agent retry a
sandbox that could never come up.

### 3. Three different "todays"

The sandbox reported a draw rate of 4.48 units/day. The same code on my laptop
reported 4.45, from identical rows. I went looking for a transcription error and
found something better.

```
Postgres (container, UTC)   2026-08-27
sandbox (UTC)               2026-08-27
host / MCP server (IST)     2026-08-28
```

Every date in the system is relative to Postgres `CURRENT_DATE` — the seed, the
consumption window, the consignment ETAs, the indent numbers. But the analysis
rebuilt its window from the local clock, and adjudication compared ETAs against
`date.today()` on the host. For the five and a half hours a day that IST and UTC
disagree, adjudication was a day ahead of the data.

That skew points the wrong way. Since overdue consignments had *stopped*
counting as cover, a day of drift throws away cover that is still valid — so a
demo recorded late in the evening could have flipped the do-nothing run into
raising an indent, destroying the exact contrast the project is built on.

One source of truth now: `db.today()`. And `get_consumption_log` returns the
window it actually queried, so the sandbox fits over the right days rather than
re-deriving them from its own clock.

While fixing it I found that `consumed_on >= CURRENT_DATE - 120` spans **121**
calendar days, so a 121-day total was being divided by 120.

### 4. The agent asked for permission bare

This one is my favourite, because it is the project's own thesis failing in
front of me.

After I disabled the harness's built-in question tool, the agent reached the
correct decision, assembled the evidence — and then called `ask_user_question`:

> *"Do you approve raising an indent of 200 nos for part TRB-4417 and sending
> the draft order email to Meridian Traction Supplies?"*

No evidence. No payload. No counterfactual. And no held tool call for the
harness to gate. That is a `confirm()` box with the dossier deleted, produced by
the agent at the exact moment the design exists to prevent it.

Qodo had already caught a version of this and I had fixed the wording; the model
simply found another route. So it is configuration now, not instruction:
`askUserQuestions` is disabled, leaving exactly one way to reach a human —
call the gated tool and let the harness hold it.

Which exposed a second trap, also caught in review: with the question tool gone,
three separate places still said *"never call `raise_indent` until a human has
approved."* Together those are a deadlock — present the dossier, wait for an
approval that cannot exist because nothing was ever held, stop. The rule now
says what was always meant: **making the call is how you ask, not how you act.**

## The bit nobody plans for: which model you pick decides whether the demo works

Identical skill text. Three free models. Three completely different behaviours:

| model | what happened |
|---|---|
| `nemotron-3-ultra` | Ignored the skill outright — no subagents, no analysis script, no adjudication. Fetched the evidence itself and tried to write its own numpy analysis in a heredoc. |
| `glm-5-2` | Upstream 429 within one second, twice. |
| `minimax-m3` | Read the skill and the scripts first, then followed the procedure exactly. |

The deterministic core does not care which model runs — the do-nothing case
passes in CI with none. But whether the *demo* works depends entirely on the
model following the skill. That is a model-selection finding, not a prompt one,
and it is the strongest argument I have for keeping judgment in code.

There is a rate-limit lesson attached. Four subagents dispatching at once is
eight requests in ten seconds. Gemini's free tier allows five per minute and the
harness has no backoff, so the turn died mid-run every time — about four
requests short of the gate. I read that off the 429 itself (`limit: 5`) rather
than assuming it was the daily quota again. The session survived intact, which
meant the rest could be driven as a second turn — and *that* is the harness's
session persistence doing exactly what it exists for, under exactly the
conditions it exists for.

## What it looks like when it works

```
Run A — TRB-4417
  *** GATE HELD ***    raise_indent{part_no: TRB-4417, qty: 200}
                       nothing written: no indent, no run-log row
  approved          -> IND-2026-0732
  *** SECOND GATE ***  send_vendor_mail{indent_no: IND-2026-0732}

Run B — BRK-2290   (one unbroken turn, 101 seconds)
  action    : no_action
  reason    : BRK-2290 is already on order. Indent IND-2026-0731 is open and
              consignment CN-9104 (300 nos) is in transit, due 2026-08-30,
              inside the 8-day stockout window.
  NO GATE — nothing to approve, because nothing should happen
```

Approving the indent does not pre-approve the mail; the second gate carries the
`indent_no` the first call actually returned. And the run log records
`no_action` as an outcome, not an error.

## What I would tell myself on Monday

**Verify the thing you are actually going to run.** I verified bubblewrap by
hand and believed I had verified the harness. Three days.

**Read the error, not the error you expect.** The 429 said `limit: 5`. I had
spent a day assuming it was the daily quota because that was the last thing that
had gone wrong.

**Let the review find the ones you cannot see.** Qodo raised eleven High-severity
findings across the build, and every one was real — including two that would have
broken the live demo outright and one arithmetic error that had a p20 cutoff
labelled p10. I disagreed with exactly one Medium finding and wrote the reasoning
on the pull request rather than silently ignoring it.

**And keep the judgment in code.** Every one of these bugs would have been
invisible if the verdict were a model's opinion. Because adjudication is ordinary
Python with tests, each one surfaced as a failing assertion or a number that did
not match — which is the whole argument, in the end, for building agents this
way.
